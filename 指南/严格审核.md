# 严格审核

日常小改动不需要复杂流程：Agent 写入 `Agent/草稿/`，人检查后指定落点即可。只有批量修改、重要知识、多人协作或来源可能变化时，才启用 Strict Review。

## 用户看到的流程

```text
选定来源 → Agent 起草 → 查看依据与改动 → 接受或退回 → 正式知识
```

底层由 [LLM Wiki Canvas](https://github.com/chicogong/llm-wiki-canvas) 提供来源快照、内容指纹、精确 Diff 和冲突阻断。内容指纹只证明文件没有变化，不证明内容正确；最终判断仍由人完成。

## 安装

需要 Node.js 22 或 24。Strict Review 是可选工具，不是打开 Qingyan Vault 的前置条件。

```sh
npm install --global llm-wiki-canvas@0.2.0
lwc serve /path/to/qingyan-vault
```

服务只绑定本机回环地址，读取普通 Markdown，不上传 Vault。安装和运行前仍应检查 npm 包名、版本与来源；不要安装无关的 `lwc` 包。

## 无外部来源的改动建议

先复制需要修改的文件到一个独立草稿目录，只编辑草稿，再创建改动建议：

```sh
lwc proposal create /path/to/qingyan-vault \
  --from /path/to/isolated-draft \
  --summary "整理项目下一步"
lwc proposal show /path/to/proposal.json
```

Agent 必须在展示 Diff 后停止，不得代替人执行接受或应用。

## 有来源的知识进入

```sh
lwc intake create /path/to/qingyan-vault \
  --source /path/to/selected-source.md \
  --target 知识/目标笔记.md \
  --generator Codex
```

只编辑命令打印的隔离草稿，然后执行 `intake show` 与 `intake propose`。人检查依据、遗漏和准确改动后，才能接受或退回。

## 人工接受

```sh
lwc proposal review /path/to/proposal.json \
  --approve <proposal-id> --reviewer "human"
lwc proposal apply /path/to/proposal.json \
  /path/to/qingyan-vault --confirm <proposal-id>
```

如果来源、草稿、建议或目标在审核后发生变化，应用必须失败。不要通过重新生成 ID 或跳过检查绕过冲突。

## 关闭与迁移

删除 Vault 内未使用的 `.lwc/` 本地工作状态并卸载 CLI，即可退出 Strict Review；正式 Markdown、WikiLinks、Bases 和 Canvas 不依赖它。`.lwc/` 可能包含本地来源路径和工作快照，不要从私人 Vault 提交或公开。
